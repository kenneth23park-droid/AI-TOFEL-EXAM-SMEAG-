# 관리자 docx 임포터 — 기획서

관리자 페이지에서 시험 원본 `.docx` 3종(문항 / 정답키 / 스크립트)을 올리면 모의고사 콘텐츠 팩을 구성하는 기능의 설계 기획.

- **정본 순서**: 이 문서 → [architecture.md](architecture.md)(런타임 계약) → [prd.md](prd.md)
- **확정된 범위 결정**: v1 = TOEFL 전용 파이프라인 완성 / 검수 = 전면 검수 강제 / 저장 = DB + 정적 내보내기
- **상태**: 기획 확정, 구현 착수 전

## 0. 이 기획이 서 있는 사실 기반

기획 전에 SET 1·SET 9 원본 5개 문서를 실측 조사했다. **아래 결론은 추측이 아니라 파일에서 직접 확인한 값이다.** 설계 판단의 근거는 전부 여기서 나온다.

| # | 실측 사실 | 설계에 미친 영향 |
|---|---|---|
| ① | **5개 문서 전체에 Heading 스타일이 0건.** 발견된 `w:pStyle` 은 `ListParagraph`/`NoSpacing`/`NormalWeb` 뿐 | 스타일 기반 구조 인식 불가. **텍스트 패턴 매칭이 유일한 수단** |
| ② | **굵게(b)·폰트크기(sz)도 판별자로 못 씀.** SET 9 리스닝은 선택지까지 전부 bold, `WRITING SECTION` 이 SET 9 는 bold sz28 / SET 1 은 rPr 비어 있음 | 서식 힌트는 보조 신호로만. 단독 근거 금지 |
| ③ | **리딩 지문 마커가 두 세트 간 공통분모 0.** SET 1 `Read an email.`/`Read a passage.` ↔ SET 9 `Read in Daily Life (Email)`/`Academic Passage` | **단일 마커 테이블 불가.** 별칭 사전이 필수 |
| ④ | **SET 9 리딩에 `Questions N-M` 마커가 아예 없음** (리스닝·라이팅에만 존재) | 문항 그룹 경계를 문항 번호에서 역산해야 함 |
| ⑤ | **선택지 표기 4종 혼재**, 세트 간 지배 방식이 반대(SET 1 = Word 자동번호 301개 / SET 9 = 수동 `A.` 지배) | 4개 경로 모두 구현 + 한 문단 뭉침 분해기 필요 |
| ⑥ | **정답키에 텍스트 번호가 전혀 없다.** 전부 `w:numPr` 자동번호라 `w:t` 에는 `populations`/`C` 만 남음 | **순수 위치 기반 정렬만 가능.** 최고 위험 요소 |
| ⑦ | SET 9 정답키는 서브 헤더도 없어 **검증 지점이 모듈당 1개**뿐 (SET 1 은 `Questions 11-12` 등 있음) | 정렬 오류를 잡을 중간 체크포인트 부재 |
| ⑧ | **표가 body 직속이 아니라 텍스트박스 안에 있음.** SET 9 표 8개 전부 `txbxContent` 하위 | body 직계 순회 파서는 **Q25-27 지문을 통째로 유실** |
| ⑨ | **`mc:Choice`/`mc:Fallback` 텍스트 중복.** 같은 지문이 2~3회 반복 추출됨 | `Fallback` 서브트리 스킵 없으면 지문이 3배로 늘어남 |
| ⑩ | **이미지→문항 매핑은 Speaking 만 신뢰 가능**(순서 기반). 리스닝 아이콘은 D 선택지·빈 문단에 앵커되고 같은 파일이 반복 재사용 | 리스닝 이미지는 자동 귀속 포기 |
| ⑪ | **자산 비대칭**: SET 1 은 오디오 있고 스크립트 없음 / SET 9 는 스크립트 있고 오디오 없음 | "스크립트 필수" 전제를 두면 SET 1 임포트가 실패 |
| ⑫ | **정답키 문서 자체에 오류 존재.** SET 9 R1-7 정답이 `correct`(7글자)인데 원본 빈칸은 `th_ _`(어간 th, 4글자) — 물리적으로 불가 | **"원본이 틀렸다"를 기록하고 덮어쓰는 기능이 필수 요구사항** |

### 여기서 나오는 가장 중요한 결론

> **"docx 업로드 → 시험 완성"은 불가능하다.** 이건 자동 변환 문제가 아니라 **파싱 + 사람 검수** 문제다.

정답키에 번호가 없어 위치로만 맞춰야 하는데(⑥), 중간 검증 지점도 없고(⑦), 원본 자체가 틀릴 수도 있다(⑫). 정답 하나가 밀리면 **그 뒤 전부가 조용히 틀리고 화면에는 아무 에러도 안 뜬다.** 학생 점수가 걸린 데이터다.

그래서 시스템의 목표를 이렇게 잡는다.

> **100% 자동화가 아니라, 검수 시간을 최소화하되 틀린 것을 조용히 통과시키지 않는다.**

**사람 검수 게이트는 제거 대상이 아니라 설계의 일부다.**

## 1. 파이프라인

```
① Upload  → ② Parse(IR) → ③ Map(profile) → ④ Review(사람) → ⑤ Publish
   docx 3종    문서 방언       시험 스키마       검수·수정        발행
```

| 단계 | 하는 일 | 실패 시 |
|---|---|---|
| ① Upload | 파일 투입, 역할 자동 판별(문항/정답키/스크립트), 프로파일 선택 | 판별 실패 → 관리자가 수동 지정 |
| ② Parse | docx → **IR(중간표현)**. 문단·표·이미지·번호매기기를 순서 보존해 평탄화 | 파싱 불가 구간을 `unparsed` 로 보존 |
| ③ Map | IR + 프로파일 → 콘텐츠 팩 초안. 항목마다 **신뢰도 + 출처 문단 인덱스** 부착 | 미인식 마커를 `unknownMarker` 로 수집 |
| ④ Review | 원본과 추출 결과를 나란히 놓고 전수 검수·수정 | 미해결 이슈가 0이 아니면 진행 불가 |
| ⑤ Publish | 실제 런타임으로 컴파일 + **렌더**까지 검증 → 통과해야 발행 | 게이트 불통과 시 발행 차단 |

## 2. 설계의 심장 — 중간표현(IR)

**파서와 매퍼를 반드시 분리한다.** IR 이 그 경계다.

- **파서**는 "Word 문서 방언"만 안다 — 문단, 표, 자동번호, 이미지 앵커, `mc:Fallback` 중복.
- **매퍼**는 "시험 구조"만 안다 — 섹션, 모듈, 블록, 문항.

분리 이득:
- IELTS 프로파일 추가가 **파서 수정 없이** 된다.
- 입력이 PDF·HWP 로 늘어나도 **매퍼는 그대로**다.
- 매퍼를 원본 없이 테스트할 수 있다(IR 픽스처만 있으면 됨).

### IR 이 반드시 갖춰야 할 것 (실측 ⑧⑨⑥ 대응)

| 요구 | 이유 |
|---|---|
| `root.iter()` 기반 순회 (body 직계 아님) | 텍스트박스 안의 표·지문을 놓치지 않기 위해 (⑧) |
| `mc:Fallback` 서브트리 스킵 | 지문 2~3배 중복 방지 (⑨) |
| 표를 문서 흐름 순서에 인라인 삽입 | 표가 지문의 일부다 (⑧) |
| `numbering.xml` 파싱해 자동번호 **복원** | 정답키·선택지 번호가 텍스트에 없다 (⑥) |
| 모든 원소에 `sourceIndex`(원본 문단 번호) + `rawText` 보존 | 검수 화면의 원본 대조와 재임포트 diff 의 기반 |

## 3. 매핑 프로파일 — 코드가 아니라 데이터, 그리고 별칭 사전

실측 ③ 때문에 설계가 바뀐 지점이다. **원래 v2 로 미루려던 "관리자가 마커를 편집하는 기능"을 v1 로 올린다.** 리딩 마커가 세트 간 공통분모 0인 이상, 새 세트마다 개발자가 붙는 구조는 성립하지 않는다.

```
profile = {
  examType, sectionOrder,
  markers[]:    { pattern, → section | module | blockKind }
  aliases[]:    { canonical, variants[] }        ← ③ 대응. 관리자 편집 대상
  blockRules[]: { blockKind, 문항 추출 규칙, 선택지 규칙 4종 }
  answerKey:    { 정렬 방식, 값 해석(단어 | 라벨→index) }
  media:        { 이미지 귀속 규칙, 오디오 id 규칙 }
}
```

### 정규화로 자동 흡수되는 것 vs 별칭 등록이 필요한 것

**정규화(소문자화 + 공백 축약 + 구두점 제거)만으로 흡수됨** — 저비용:

| 변형 | 예 |
|---|---|
| 단수/복수 + 마침표 | `Fill in the blank` ↔ `Fill in the blanks.` |
| 대소문자 | `Module 1` ↔ `MODULE 1` |
| 후행 공백 | `WRITING SECTION ` ↔ `WRITING SECTION` |
| cloze 힌트 공백 | `1 popul_ _ _` ↔ `1br_ _ _` → `(\d+)\s*([A-Za-z]+)((?:_ ?)+)` |

**명시적 별칭 등록이 반드시 필요함** — 정규화로 절대 안 붙음:

| SET 1 | SET 9 |
|---|---|
| `Read an email.` | `Read in Daily Life (Email)` |
| `Read a passage.` | `Academic Passage` |
| `Read a text message chain.` | (대응 없음) |
| `READING SECTION MODULE 1` (한 줄 결합) | `Module 1` + `Reading` (두 줄, 순서 반대) |

### 두 세트에서 이미 검증된 공용 마커 (별칭 불필요)

`WRITING SECTION` · `Build a sentence` · `Make an appropriate sentence.` · `WRITE AN EMAIL` · `SITUATION` · `YOUR EMAIL SHOULD` · `WRITE for an ACADEMIC DISCUSSION` · `SPEAKING SECTION` · `Task 1` · `Task 2` · `Listen and Repeat` · `Answer the interviewer's questions.` · `Listen to a conversation.` / `an announcement.` / `a talk.` / `the question and select the best response from the choices.` · `Position A~D`

**→ 라이팅·스피킹·리스닝 지시문 계층은 패턴 테이블 하나로 커버된다. 무너지는 곳은 리딩 섹션과 정답키 정렬, 이 둘뿐이다.** 개발 노력을 여기 집중한다.

## 4. 관리자 화면 3개

### ① Import
파일 드롭 → 역할 자동 판별 → 프로파일 선택 → **파싱 리포트를 즉시 표시**.

리포트의 핵심은 딱 하나: **섹션별 인식 문항 수 vs 정답키 개수 대조표.** 이게 어긋나면 그 아래 모든 게 무의미하므로 가장 먼저, 가장 크게 보여준다.
미인식 마커(`unknownMarker`) 목록도 여기서 노출하고, 그 자리에서 별칭으로 등록할 수 있게 한다(③ 대응).

### ② Review — 전면 검수 강제
좌측 원본 문단 / 우측 추출 결과. 신뢰도 배지(확실 / 의심 / 미해결), 인라인 수정, 상단에 미해결 카운터.

검수 강제 방식은 **문항마다 "확인" 체크**이며, 전 문항 확인 전에는 발행 버튼이 비활성이다. 실무 속도를 위해:
- 의심·미해결만 필터링해 훑는 모드
- 블록 단위 일괄 확인(같은 지문의 5문항을 한 번에)
- 이전 세트와 동일한 패턴은 자동으로 "확실" 등급 부여

**원본 오류 override 기능** (⑫ 대응, 실제로 발생한 케이스):
정답키가 틀렸을 때 관리자가 값을 덮어쓰되, `answerKeyRaw` 에 원본 표기를 보존하고 사유를 남긴다. 발행물에 override 목록이 따라붙어 나중에 추적 가능해야 한다.

### ③ Preview & Publish
학생이 볼 화면을 그대로 미리보고, 게이트 전부 통과 시 발행.

## 5. 미리보기는 컴파일이 아니라 **렌더**까지 해야 한다

이건 SET 9 을 손으로 넣으면서 실제로 겪은 사고에서 나온 요구사항이다.

SET 9 콘텐츠 팩은 컴파일 테스트를 **전부 통과했다**(95화면 / 120문항 / validateScreen 전수 / 미디어 경로 전수 해석). 그런데 브라우저에서 실제로 렌더해보니:

```
placeholders: writing.q.W1.01 … W3.01          ← 12화면이 "Renderer not loaded"
runtimeErrors: [SG_LISTEN] question not found in content pack: L1-1 … L2-15   ← 47건
```

**리스닝 47문항 전부와 라이팅 12화면이 빈 껍데기로 렌더되고 있었다.** 원인은 렌더러들이 활성 콘텐츠 팩이 아니라 `window.SMEAG_SET1` 을 하드코딩 조회한 것이었고, 컴파일 테스트는 DOM 을 만들지 않으므로 이걸 **구조적으로 잡을 수 없었다**.

→ **발행 게이트는 반드시 헤드리스 브라우저에서 전 화면을 실제 렌더**해 placeholder / null / 예외가 0인지 확인해야 한다. 컴파일 통과는 발행 근거로 불충분하다.

그리고 미리보기는 **이미 만들어 둔 `exam-compile.js` + 렌더러 5종을 그대로 로드**한다. 검증 로직을 두 번 구현하지 않으므로 "임포터는 OK 했는데 실제 시험에서 깨지는" 상황이 원천 차단된다.

## 6. 발행 차단 게이트

하나라도 걸리면 발행 불가.

| 게이트 | 근거 |
|---|---|
| **정답 개수 ≠ 문항 개수** | ⑥⑦ — 위치 정렬 사고를 잡는 유일한 자동 방어선. **최우선** |
| MCQ `answer` index 가 `choices` 범위 밖 | 채점 불능 |
| cloze `{{n}}` 개수 ≠ 해당 블록 문항 수 | 빈칸/정답 어긋남 |
| cloze 정답이 어간·글자수와 불일치 | ⑫ 실제 검출 사례. `popul`+6=11=`populations` 식 교차검증 |
| 오디오·이미지 참조 미해결 (존재 + 크기>0 + 재생길이>0) | 무음 시험 방지 |
| **오디오 검증(`tools/verify_audio.py`) 계층 0~2 에서 FAIL** | §6.1. 잘림·전구간 무음·화자 턴 결손·낡은 음원·파일 뒤바뀜 |
| **스크립트를 고쳤는데 음원이 낡음(신선도 해시 불일치)** | §6.1 계층 0. 같은 URL 에 덮어쓰는 구조라 사람 눈으로는 안 보인다 |
| 콘텐츠 팩이 참조하는 mp3 가 오디오 매니페스트에 없음 | 팩↔매니페스트 교차. 재생 시점에 404 |
| **헤드리스 전 화면 렌더에서 placeholder/예외 > 0** | §5 |
| 컴파일러 blocking warnings | 런타임 화면 빔 |
| 미검수 문항 존재 | 전면 검수 강제 |

### 6.1 오디오 검증 게이트 — 계층 구조

사람이 400개 mp3 를 들어볼 수 없으므로 기계가 계층별로 훑는다. 판정은 `PASS` / `WARN` / `FAIL` 3단계이며 **FAIL 하나라도 있으면 발행 불가**, WARN 은 검수 화면에 표시해 사람이 본다.
**없는 계층은 조용히 통과시키지 않고 `SKIP` 으로 리포트에 사유와 함께 남긴다.** "검사하지 않았다"와 "검사해서 통과했다"를 구분하지 못하면 게이트가 있는 척만 하게 된다.

| 계층 | 검사 | 무엇을 잡는가 | 필요 도구 | 비용(SET 9, 40개) |
|---|---|---|---|---|
| **0** 매핑·신선도 | 항목↔파일 존재, 스크립트+음성정책 sha256, mp3 바이트 해시, 고아 파일, 팩 교차확인 | **문항은 있는데 음원 없음** / **스크립트를 고쳤는데 재생성 안 함** / 파일 이름 뒤바뀜 / 여러 문항이 같은 mp3 | 없음 (표준 라이브러리) | < 1초 |
| **1** 파일 무결성 | 0바이트·손상, 코덱/샘플레이트/채널 허용목록 | 생성이 중간에 끊긴 파일, 엔진 혼용으로 튀는 제원 | `ffprobe` | ≈ 6초 |
| **2** 신호 분석 | 예상 길이 대비 실제 길이 비율(단어수/wpm), 무음 비율·선행/후행 무음·내부 공백, 검출 턴 수 vs 대본 세그먼트 수, 라우드니스/클리핑 | **잘린 음원**, **전 구간 무음**, **화자 턴 통째 결손**, 안 들리는 볼륨 | `ffmpeg` | ≈ 13초 |
| **3** 텍스트 대조 | STT 전사 ↔ 대본 WER (판정은 `smeag-local-ai/qa/stt_loopback.py` 의 `classify()` 재사용) | **지문 대신 문항 질문문이 녹음된 경우** — 다른 계층은 원리적으로 못 잡는다 | 로컬 STT (faster-whisper 등) | 수 분 |

**계층 3 이 없을 때의 degrade 규칙**

| 상황 | 동작 |
|---|---|
| STT 백엔드 있음 | 계층 3 실행. WER > reject → FAIL(발행 차단), > warn → WARN |
| STT 백엔드 없음 | 계층 3 = `SKIP`. **PASS 로 위장하지 않는다.** 리포트와 발행물에 "내용 대조 미수행" 과 어떤 백엔드를 설치하면 켜지는지가 함께 남는다 |
| 계층 0~2 는 항상 실행 | 의존성 0(계층 0)부터 쌓아 올린 구조라, STT 가 없어도 위 3대 사고 중 2개(결손·미재생성)는 여전히 막힌다 |

임계값은 `tools/verify_audio.py` 의 `THRESHOLDS` 딕셔너리 **한 곳**에만 있고 각 값에 실측 근거가 주석으로 붙어 있다. 계층 3 의 임계값은 `stt_loopback.py` 의 상수를 **참조만** 한다(복사본 금지). 화면·CLI·테스트가 갈라진 숫자를 보면 "테스트는 통과인데 게이트는 차단"이 난다.

**테스트 편입**: `studyground/tests/test_audio_manifest.py` 가 계층 0~1 을 매 실행마다 돌린다(≈5초). 계층 2 는 `-m slow`, 계층 3 은 `-m stt` 로 분리돼 있다.

## 8. 오디오 — 파일 / 스크립트 / 둘 다 모두 허용

자산이 비대칭이라(⑪) **어느 하나를 필수로 요구하면 안 된다.**

| 세트 | 스크립트 | 오디오 |
|---|---|---|
| SET 1 | **없음** | mp3 32개 있음 |
| SET 9 | 있음(단, M2 본문 누락) | **없음** → TTS 생성 |

### 8.1 세 가지 입력 모드를 모두 지원한다

| 모드 | 입력 | 처리 | 대표 사례 |
|---|---|---|---|
| **A. 오디오만** | mp3 폴더 | 파일명 → 문항 범위 매핑 | SET 1 |
| **B. 스크립트만** | 스크립트 docx | 전사 → TTS 합성 | SET 9 |
| **C. 둘 다** | mp3 + 스크립트 | 파일이 있으면 **파일 우선**, 없는 구간만 TTS 로 메움 | 혼합·부분 보강 |

**모드 C 가 기본 동작이다.** A 와 B 는 C 의 특수 케이스일 뿐 별도 코드 경로가 아니다. 임포터는 항상 "문항별로 오디오 소스가 무엇인가"를 결정하는 하나의 해석기를 돌리고, 우선순위는 다음과 같다.

```
① 업로드된 실제 녹음         (최우선 — 사람이 직접 올린 것)
② 매핑된 기존 mp3 폴더
③ 스크립트 → TTS 합성
④ 없음 → "오디오 없는 문항"으로 보고 (발행 게이트에 걸림)
```

둘 다 있으면 **실제 녹음이 이긴다.** 스크립트는 이 경우 버려지지 않고 **전사(transcript)로 보존**된다 — 나중에 관리자 검수 화면에서 음원과 대조하거나, 접근성 자막·재합성에 쓴다. 이 전사가 §6.1 계층 3 의 기준 대본이 되므로, 녹음이 이겼다고 스크립트를 버리면 **내용 대조 계층이 통째로 꺼진다.**

### 8.1.1 오디오 파이프라인 — 생성 직후 자동 검증이 들어가는 자리

**요구사항 원문**: *"tts로 녹음된 mp3파일을 검증 받는 단계를 프로그램 상에 넣어야 한다. 또한 오디오 스크립트를 임포트해서 문항 및 오디오 파일 만들때도 검증을 자동으로 해서 문제를 제거해야 한다"*

검증은 **관리자가 버튼을 눌러 실행하는 별도 메뉴가 아니다.** 오디오가 만들어지는 모든 경로의 마지막 단계로 붙어 있고, 끄려면 명시적으로 꺼야 한다(`--no-verify`).

```
스크립트 임포트 → 구간 판정(§8.3) → TTS 합성 → ★검증(계층 0~2, --update-index)★ → 검수 → 발행
                                     ↑ 실패하면 여기서 멈춘다. 발행 큐로 넘어가지 않는다.
업로드된 녹음   → 매핑 추정(§8.2) ──────┘
```

| 단계 | 하는 일 | 실패 시 |
|---|---|---|
| 합성/수집 직후 | 생성기가 **자동으로** `tools/verify_audio.py --update-index` 를 호출 | 리포트에 FAIL 이 있으면 **생성기 자체가 non-zero 로 종료**. 조용히 성공하지 않는다 |
| 신선도 기준선 | 같은 호출이 `.audio-index.json` 에 스크립트+음성정책 해시를 기록 | 지금이 "음원과 대본이 일치한다"고 말할 수 있는 유일한 시점이다. 나중에 스크립트만 바뀌면 해시가 어긋나 계층 0 이 FAIL |
| 임포트 재실행 | 매니페스트를 다시 쓰고 다시 검증 | 바뀐 항목만 STALE 로 뜬다 → 재생성 대상이 자동으로 특정된다 |
| 발행 | §6 게이트가 같은 검증기를 다시 돌려 최종 확인 | FAIL 이면 발행 차단 |

이미 배선된 생성기(같은 구조를 새 생성기에도 적용한다):

| 생성기 | 대상 | 검증 호출 |
|---|---|---|
| `studyground/tools/tts_set9.py` | `sg2/media/audio/set9/` | 합성 후 `verify_audio.py --manifest sg2/tts-manifest.set9.json --update-index --base <out 의 기준 폴더>` |
| `studyground/sg2/tools/tts_multivoice.py` | `sg2/media/tts/` | 합성 후, `sg2/tts-voices*.json` 의 **합집합**으로 파생 매니페스트를 만들어 같은 검증기에 통과시킴 |

파생 매니페스트가 합집합인 이유: `media/tts/` 를 여러 생성기가 나눠 쓰고 있어서, 한 생성기의 항목만 선언하면 나머지 파일이 전부 "고아 mp3" 와 "팩이 참조하는데 매니페스트에 없는 음원"으로 잡혀 **남의 파일 때문에 발행이 막힌다.** 폴더 단위로 선언이 완결돼야 게이트가 성립한다.

`--update-index` 를 생성 시점에 거는 이유는 §6.1 계층 0 의 신선도가 **"지금 이 순간부터의 변경"** 만 탐지하기 때문이다. 생성 밖에서 기준선을 세우면 그 시점의 mp3 가 대본과 맞는다는 보장이 없다 — 그건 계층 3(STT)만이 말할 수 있다.

### 8.2 파일명 → 문항 매핑은 자동 추정 + 확인

SET 1 오디오 파일명에 문항 범위가 들어 있으나 구분자가 제각각이다.

```
1.mp3 … 7.mp3, "8 - Conversation 1.mp3", "9 -10 -Conversation 2.mp3",
"11-12 Announcement.mp3", "13 -14 Announcement.mp3", "15 -18 Academic talk.mp3"
```

`(\d+)\s*[-–]?\s*(\d+)?` 로 범위를 추정하되, **추정 결과를 검수 화면에서 확인받는다.** 파일명 규칙이 세트마다 바뀔 수 있으므로 자동 매핑을 신뢰하지 않는다(③과 같은 이유).

### 8.3 스크립트에 본문이 없는 구간 — 실제로 발생함

SET 9 스크립트의 MODULE 2 구간에는 **문항 질문문 15개만** 있고 Q4~Q15 가 묻는 **대화·강의 본문이 없다.** 즉 "스크립트가 있다"고 해서 전 구간을 TTS 로 만들 수 있는 게 아니다.

임포터는 이걸 **구간 단위로 판정**해야 한다:
- 짧은 응답형(short response) → 질문문 자체가 음원이다. 그대로 합성 가능.
- 대화·강의형 → **본문 전사가 있어야** 합성 가능. 질문문만 있으면 합성 불가.

이 구분 없이 "스크립트 있음 = 합성 가능"으로 처리하면 **문항 질문문을 음원으로 만들어 버리는 치명적 오류**가 난다(학생이 지문 대신 문제를 듣게 됨).

이 오류는 **§6.1 계층 3(STT 내용 대조)만이 사후에 잡을 수 있다.** 파일은 멀쩡히 존재하고, 길이도 무음 비율도 정상이라 계층 0~2 는 전부 통과한다. 그래서 구간 판정(사전 방어)과 STT 대조(사후 방어) 둘 다 필요하고, STT 백엔드가 없는 환경에서는 이 구멍이 열려 있다는 사실이 리포트에 `SKIP` 으로 남아야 한다.

### 8.4 본문이 없을 때의 마지막 수단 — 제약 하 집필

원본 전사가 없고 녹음도 없으면 선택지는 둘뿐이다: 그 문항을 포기하거나, **정답키 제약에 맞춰 지문을 새로 집필**하는 것.

집필을 지원하되 반드시 다음을 강제한다(SET 9 L2 에서 실제로 수행한 절차):
1. 문항·선택지·정답키는 **원본 그대로 고정**. 지문만 쓴다.
2. 키 정답이 **유일하게** 성립하고 오답이 전부 배제되도록 쓴다.
3. **역채점 검증** — 정답을 모르는 독립 검증자가 지문만 보고 문제를 풀어 키와 대조한다. 불일치·저확신·경합 선택지가 있으면 지문을 고친다.
4. 산출물에 `origin: "authored"` 를 남기고 **원본 확보 시 교체 대상**임을 명시한다.

### 8.5 임포트 결과에 반드시 포함할 것

**"오디오 없는 문항" 목록**을 문항 단위로 명시한다. 구멍이 조용히 묻히면 무음 시험이 나간다.
각 문항에 대해 오디오 출처(`recorded` / `mapped` / `tts` / `authored-tts` / `none`)를 기록해 발행물에 함께 싣는다.

여기에 **검증 결과도 문항 단위로 함께 싣는다**: 계층별 판정(`PASS`/`WARN`/`FAIL`/`SKIP`), 판정 사유(수치 포함), 그리고 **어느 계층이 안 돌았는지**. WARN 목록이 발행물에 남지 않으면 "사람이 보기로 한 것"이 아무도 안 본 것이 된다.
