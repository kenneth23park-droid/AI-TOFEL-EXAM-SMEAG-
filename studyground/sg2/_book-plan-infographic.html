First, what this test actually is

먼저 — 이 시험의 실제 포맷

Read from the live set data in config/_set9_fragments/. This is New TOEFL, not classic iBT. The book must be built against these task types, not the ones people usually assume. 세트 원본에서 직접 확인한 값이다. 고전 iBT가 아니라 New TOEFL 포맷이므로, 연습북은 아래 과제 유형에만 맞춰 설계한다.

Why this matters: chapter topics like “Prose Summary” or “integrated speaking” do not exist in this test. The 40 chapters are anchored to the four task families above. 이 확인이 중요한 이유: 흔히 쓰는 iBT식 장 구성은 이 시험에 없다. 40개 장은 위 과제 유형에서만 도출한다.
01

One source, five outputs

하나를 저작하면 다섯 갈래로 나간다

A chapter is stored in the same JSON schema the exam engine already reads (modules → blocks → questions). No new content format is invented, so every existing tool — duplicate check, TTS, scoring — keeps working. 장 하나를 기존 세트 스키마 그대로 저장한다. 새 포맷을 만들지 않으므로 중복검사·TTS·채점 도구가 그대로 재사용된다.

02

Authoring pipeline — LangGraph with quality gates

저작 파이프라인 — 게이트를 통과해야 사람 검수로 올라간다

A chapter is not “generated and accepted.” It is drafted, then attacked by four independent gates in parallel. Any failure sends it back to revise, up to three rounds; only survivors reach the human review queue. 생성하고 끝이 아니다. 초안을 네 개의 게이트가 동시에 검증하고, 하나라도 걸리면 최대 3회까지 되돌려 고친다. 통과한 것만 사람 검수 큐로 올라간다.

BMAD holds the contract. The plan, stories and acceptance criteria for this module live in docs/bmad/ alongside the existing set, and architecture.md stays the tiebreaker when documents disagree. BMAD가 계약을 잡는다. 이 모듈의 PRD·스토리·인수조건을 기존 docs/bmad/에 추가하고, 문서 간 충돌 시 architecture.md가 이긴다는 기존 규칙을 그대로 따른다.
03

“Searchable” means three things

검색 가능 — 세 층으로 보장한다

1 · Text layer텍스트 레이어

HTML with print CSS → headless Chrome --print-to-pdf. Never a rendered image, so Ctrl+F works inside the PDF. Diagrams are inline SVG for the same reason. 이미지로 굽지 않으므로 PDF 안에서 그대로 검색된다. 그림도 같은 이유로 SVG.

2 · PDF outline북마크 3단

Book → chapter → part, injected after the build, plus document title and keyword metadata. 권 → 장 → 파트 3단 북마크와 문서 메타를 빌드 후 주입한다.

3 · Back-of-book index권말 색인

Term → page, built in two passes: first build emits anchor positions, second build prints real page numbers. 용어→페이지 표를 2-pass로 만든다. 1차에서 좌표를 뽑고 2차에서 페이지 번호를 확정.

Plus a sidecar book-index.json so the site can search the books too — a PDF text layer is invisible to the web app. 여기에 사이드카 색인을 더한다. PDF 텍스트 레이어는 웹앱이 못 읽으므로, 사이트 검색은 이 JSON이 담당한다.
04

Audio route & admin surface

오디오 경로와 어드민 화면

Listening audio리스닝 오디오

Script lives inside the chapter JSON → rendered by the existing tts_multivoice.py with the voice-casting config. The printed page carries a QR + short URL + track number; an offline bundle ships the same tracks with a manifest. 스크립트를 장 JSON에 정본으로 두고 기존 멀티보이스 TTS로 렌더한다. 종이에는 QR·짧은 URL·트랙번호를 싣고, 오프라인용으로 같은 트랙을 매니페스트와 함께 묶는다.

admin-books.html새 어드민 화면 1장

Chapter list with status badges (draft → gates passed → reviewed → built), preview, gate report, build button, version tag, download, and “publish as exam set.” Answer-key and teacher editions stay behind staff permission. 장 목록·상태 배지·미리보기·게이트 리포트·빌드·버전·다운로드, 그리고 '시험으로 출제' 버튼. 정답지와 교사용은 스태프 권한 뒤에 둔다.

Where the build runs: headless Chrome cannot run in a Vercel function, so PDFs are baked by a local script (tools/build_book.py) and only the finished files go to Supabase Storage. The admin page manages artifacts; it does not compile them. 빌드 위치: 헤드리스 크롬은 서버리스에서 못 돌리므로 PDF는 로컬 스크립트로 굽고 결과 파일만 Storage에 올린다. 어드민 화면은 산출물 관리자다.

06

Three decisions needed before P0

착수 전에 정해야 할 세 가지

  1. Book shape — four books × 10 chapters (assumed), or one combined 10-chapter book covering all four sections? 4권×10장으로 잡았는데, 4섹션을 한 권 10장에 합칠 수도 있다. 분량이 1/4로 준다.
  2. Who gets the PDF — admin download only, or students too? Students means watermark + expiry. 어드민 전용인지 학생 배포까지인지. 배포하면 워터마크·기간 제한이 필요하다.
  3. Print spec — A4, and is black-and-white printing assumed? It changes how every diagram is coloured. A4 여부와 흑백 인쇄 전제. 도해 색 설계가 여기서 갈린다.
